# 03 — 录入「汇总」文档里的 MCP 条目

**What to build:** 「汇总」文档里标了 MCP 的 21 个条目进目录。装法实际试通过的登记为 MCP——现有用户在安装器的 MCP 分组里马上就能看到并装上；没试通的登记为外部项目，只给说明和链接。

**Blocked by:** 02
**Status:** ready-for-agent
**Impl:** ready

- [ ] 范围是 `research/outline-entries.md` 里标签含 `MCP` 的全部条目，包括同时标了 `工具` 的 Graft、code-review-graph、FastCode、Headroom。每个条目在目录里恰好一条。
- [ ] 每条的连接方式只取它官方说明里给出的（本地进程的启动命令，或远程地址）；要向用户要的环境变量逐个写明是否必填、是什么、去哪申请。
- [ ] 「试通」的标准：经安装器、用真实的宿主命令、在临时配置目录里装一次，两个宿主的配置里都出现这一条。做法照 CLI 层规范「发布前在本机核对」：主目录和两个宿主的配置目录都指到临时目录并在脚本开头断言，真实的配置不变。
- [ ] 需要 key 而手头没有的：配置写得进去就算试通，说明里注明没有带 key 验证过。
- [ ] 启动方式写不进现有条目格式的（参数带空格或引号、要先克隆再构建、要 docker 部署、只支持一个宿主之外的做法等），登记为外部项目，并在试通记录里写明原因。
- [ ] 同时标了 MCP 和工具的四个，只登记主要用法那一种。
- [ ] 每条有一个用途（它在文档里所在的大标题）、中英文各一句说明（写「它做什么」，句末不加句号）、官方链接。名字是小写 kebab-case。
- [ ] 不给任何条目加推荐标记。
- [ ] 试通记录写进任务目录的 `research/`：每条用了什么连接方式、在哪个宿主下试的、结果如何、没试通的原因。
- [ ] 目录校验命令对仓库真实的目录数据通过。
