# 目录按用途分类，第三方 skill 改由命令安装，并收录「汇总」文档的条目

> 术语以仓库根 `GLOSSARY.md` 为准：正文说「宿主」，界面文案里它显示为「AI Agent」。本任务引入的词——用途、推荐、外部项目、第三方 Skill、安装范围（全局 / 项目）——已经写进术语表。
> 相关的设计决定：ADR-0001（安装器自成一体的三条规矩）、ADR-0002（目录运行时现拉）、ADR-0003（第三方 skill 不收进仓库，由 skills CLI 装）。
> 本 spec 的决策来自 2026-10-10 的访谈（Q1–Q34），逐条记在同目录的 `research/interview-decisions.md`；「Further Notes」里单列的推断没有经维护者逐条确认。
> 维护者于 2026-10-10 确认了本 spec。
> 同日工单 01 在对比页上选定了新画面的画法（混合列表用「类型分段」），记在同目录的 `ui-direction.md`；本 spec 里说「每行标出类型」「行上有第三方标记」「推荐的在前、其余按名字」的几处随之改成了分段的说法；评审指出段标题会滚出屏幕后，维护者又定下列表下方加一行「类型」。

## Problem Statement

维护者手里有一份「汇总」文档，记着他挑过的一百多个 AI 工具链条目，想让别人能通过安装器用上它们。现在做不到：

- **找不到东西。** 安装器的主菜单按类型分四组（Skill、MCP、工具、应用项目）。用户想的是「我要给 AI Agent 加上联网搜索」，却得分别进 Skill 和 MCP 两组去翻。条目从十几个涨到一百多个之后，按类型平铺等于没有分类。
- **第三方 skill 收不进来。** 规则是第三方 skill 必须整包收进本仓库。要收的有三十来个仓库、上百个 skill：逐个搬运、改目录名、跟进上游更新，人工做不动；其中约一半（靠插件才完整的、本体是另一个程序的）复制进来也是残缺的；有一个 skill 自己就带一万三千个文件，会把仓库的文件列表撑到安装器拒绝安装任何 skill 的地步。
- **只能装到全局。** 安装器装的 skill 和 MCP 对这台机器上的所有项目生效。用户只想在某一个项目里用的，装不了。
- **装不了的条目没有合适的去处。** 「应用项目」这个名字只说得通要自行部署的应用，装不下文档里的开发库和资源合集。

## Solution

- 主菜单改成按**用途**进入：第一行是「推荐」——维护者放进本仓库的 skill 都在这里——下面是 10 个用途，每个旁边写着条目数。进入一个用途，看到的是这个用途下的全部条目，Skill、MCP、工具、外部项目在同一张表里，按类型分段、段首写明类型（第三方 Skill 另成一段）；可以一次勾选不同类型的条目，确认后安装器按各自的方式逐个装。
- **第三方 Skill** 不再收进仓库。目录只按仓库登记；用户勾选后，安装器在后台调用通用的 skill 安装程序（`npx skills add`）把它装进宿主，用户始终只看到安装器自己的画面。一个仓库里有多个 skill 的，安装器把它们列出来让用户当场勾选。
- 装 Skill 和 MCP 之前多一问：装到**全局**，还是装到**项目**（运行安装器时所在的目录）。缺省全局。
- 「应用项目」改名**外部项目**，装不了、只给说明和链接的条目都放这里。
- 「汇总」文档的条目全部进目录。装法实际试通过的作为组件，没试通的先作为外部项目。

## User Stories

### 找条目

1. 作为用户，我想主菜单按用途列出条目，这样我按「要解决什么问题」就能找到东西，不用先知道它是 Skill 还是 MCP。
2. 作为用户，我想每个用途旁边写着它有多少个条目，这样我知道进去会看到多少东西。
3. 作为用户，我想没有条目的用途不出现在主菜单上，这样不会进到一张空表里。
4. 作为第一次用的用户，我想主菜单第一行是「推荐」，进去就是维护者自己维护或收进仓库的 skill，加上他另外标了推荐的条目，这样我不用逛遍 10 个用途就知道先装什么。
5. 作为用户，我想「推荐」里一个条目都没有时，这一行不出现。
6. 作为用户，我想进入一个用途后在一张表里看到它的全部条目，各种类型都在这一张表里。
7. 作为用户，我想看得出每个条目的类型——同类型的排在一段，段首写着类型；列表滚动之后，光标所在那一条的类型仍写在列表下方——这样我知道勾了它会发生什么。
8. 作为用户，我想第三方 Skill 自成一段、段首标明「第三方」，这样我知道它的内容直接来自作者，不是维护者检查过的那一份。
9. 作为用户，我想用途的列表里带推荐标记的条目看得出来。
10. 作为用户，我想外部项目排在列表最下面单独一段，并写明只给链接，这样我不会以为勾了它就会装上什么。
11. 作为用户，我想光标停在哪一行，列表下方就显示那一条的说明。
12. 作为用户，我想一次勾选几个不同类型的条目，一起确认、一起装。
13. 作为用户，我想一个都不勾就确认时回到上一步。
14. 作为用户，我想「推荐」里的列表和用途里的列表是同一种画面、同一套操作。
15. 作为用户，我不想主菜单上再有按类型分的入口——同一个条目只该在一个地方找到。
16. 作为用户，我想做完一轮后回到主菜单，可以接着装别的用途下的条目。

### 宿主与安装范围

17. 作为检测到不止一个宿主的用户，我想进入列表前先选装进哪些宿主，只问一次。
18. 作为只检测到一个宿主的用户，我想不被问这一句，直接用它。
19. 作为用户，我想选完宿主之后被问装到全局还是项目，光标缺省停在全局，按一下回车就过。
20. 作为用户，我想「项目」指的就是我运行安装器时所在的目录，不需要我再确认一遍路径。
21. 作为用户，我想列表里每个条目的状态是按我选的宿主和安装范围显示的，这样我知道在这个范围里它装没装过。
22. 作为用户，我想工具不受安装范围影响，它的状态和装法与范围无关。
23. 作为一个宿主都没检测到的用户，我想仍然能进入用途、看到全部条目，其中组件不可选并写明原因，外部项目照常可选。
24. 作为用户，我想在汇总里看到每一项会落到哪个位置，装到项目的写成相对当前目录的路径。

### 本仓库的 skill

25. 作为用户，我想把本仓库的 skill 装到项目时，它落在项目目录下这个宿主的 skill 目录里。
26. 作为用户，我想装到项目时的状态判断、版本对比、覆盖前的询问都和装到全局时一样。

### 第三方 Skill

27. 作为用户，我想勾了一个只含一个 skill 的第三方 Skill 时不被多问，直接进汇总。
28. 作为用户，我想勾了一个含多个 skill 的第三方 Skill 时，接着看到它里面的 skill 清单，每个带一句中文说明，由我勾选要哪几个。
29. 作为用户，我想在这张清单里一个都不勾就确认时，这一条不装，其余勾选的照常。
30. 作为用户，我想清单里每个 skill 写着它在所选宿主和范围下装没装过。
31. 作为用户，我想有特别要留意之处的 skill（要付费账号、会关掉浏览器、默认加署名）在它的说明里写明。
32. 作为用户，我想执行前在汇总里看到将要运行的完整命令。
33. 作为用户，我想安装第三方 Skill 时终端上不出现那个安装程序自己的标志、框线和进度，也不被它提问——从头到尾只有安装器自己的画面。
34. 作为用户，我想目标位置已经有同名目录时先问我，缺省不覆盖。
35. 作为用户，我想每个 skill 在每个宿主下各有一行结果，一项失败不影响其余项。
36. 作为用户，我想失败的那一行告诉我是哪一步、退出状态是几，我可以照汇总里的命令自己再跑一遍看原因。
37. 作为用户，我想确认前看到一句提醒：第三方 Skill 装的是作者当时的最新版。
38. 作为用户，我不想因为用了安装器而让那个安装程序把我的安装统计发出去。
39. 作为用户，我想把第三方 Skill 装到项目时，它落在项目目录里而不是全局。
40. 作为用户，我想某个第三方 Skill 不支持我选的某个宿主时，它在那个宿主下显示不支持，在别的宿主下照常能装。
41. 作为用户，我想功能靠插件才完整的第三方 Skill 在说明里写明：这样装上是基本功能，完整功能要按它官方的方式装插件。

### MCP

42. 作为 Claude Code 的用户，我想把 MCP 装到项目时，它写进项目目录里的配置，只对这个项目生效。
43. 作为 Codex 的用户，我想把 MCP 装到项目时，它写进项目目录里 Codex 的配置；Codex 只对受信任的项目读这份配置，这一点要事先告诉我。
44. 作为用户，我想把需要 key 的 MCP 装到项目时照样能装，但在确认前被明确提醒：key 会以明文写进项目里的哪个文件，不要把它提交或发给别人。
45. 作为用户，我想 MCP 的状态按所选范围显示：选项目时看的是项目里的配置，选全局时看的是用户级配置。
46. 作为用户，我想 key 怎么问、命令怎么展示、已配置的怎么覆盖，都和现在一样。

### 工具

47. 作为用户，我想工具和别的类型一起勾选后，它的安装命令仍然完整展示、确认后才执行、执行后复核。
48. 作为用户，我想工具的命令执行时它自己的输出仍然直接显示，要输密码时我答得了。
49. 作为用户，我想不支持我这个系统、或需要别的宿主的工具仍然显示为不可选并写明原因。

### 外部项目

50. 作为用户，我想勾了外部项目并确认后，在这一轮的最后看到它们各自的说明和链接。
51. 作为用户，我不想安装器替我打开浏览器——一次勾好几个时会弹出一堆网页。
52. 作为用户，我想只勾了外部项目时不被问「是否执行」，因为没有要执行的东西。

### 汇总、执行与结果

53. 作为用户，我想确认前看到一份汇总，列出这一轮要做的每一件事。
54. 作为用户，我想「将执行的命令」把 MCP、工具、第三方 Skill 的命令都列出来，看到的就是之后执行的。
55. 作为用户，我想在汇总上可以选开始安装、返回修改或取消；返回修改时我的勾选还在。
56. 作为用户，我想结束时看到每一项的结果和合计。

### 维护目录

57. 作为维护者，我想用途的清单记在目录里，增删改一个用途只需要提交本仓库，不用发 npm 版本。
58. 作为维护者，我想给本仓库 skill 以外的每个条目标一个用途、可选地标上推荐。
59. 作为维护者，我想登记一个第三方 Skill 时只写它的仓库、里面有哪些 skill、各自一句说明。
60. 作为维护者，我想凡是放进本仓库的 skill 都自动出现在「推荐」里，不用为它做任何标注，也不用改 skill 清单的格式——另一个工具也在读它。
60a. 作为维护者，我想个别本仓库的 skill 除了在「推荐」里，还能另外出现在某一个用途下。
61. 作为维护者，我想目录校验命令查得出：条目没有用途、用途不在清单里、第三方 Skill 条目写坏了。
62. 作为维护者，我想有一条命令替我核对目录里登记的第三方 Skill 与作者仓库的现状——仓库还在不在、改没改名、里面的 skill 多了少了——这样条目失效时不必等用户来报。
63. 作为维护者，我想已经发出去的旧版安装器读到新目录时照常工作。
64. 作为维护者，我想「汇总」文档里的每个条目都进目录；装法没有实际试通过的先作为外部项目，试通了再改成组件。
65. 作为维护者，我想 README、安装器的说明、开发规范里的用词都换成新的。

## Implementation Decisions

### 目录的格式

- **只做向后兼容的改动，两个文件的格式版本号都不升。** 安装器已经发布到 npm（0.2.0），发布前可以直接改格式的那条例外已经作废。新增的都是可选的字段和数组；旧版安装器忽略它们，照旧显示四个分组。
- **`catalog.json` 里登记外部项目的那个数组不改键名**，只改叫法：术语、界面文案、文档里叫外部项目，数据里的键仍是原来的。改键名是不兼容的改动。
- **skill 清单一个字不动。** 它在对 A Team Workflow 的承诺之内，给它的条目加字段会不会坏在本仓库内无从验证；承诺里还写明清单不登记内容不在本仓库的 skill。所以第三方 Skill 记在 `catalog.json`；本仓库的 skill 不需要任何标注就在「推荐」里，个别要另外出现在某个用途下的，那个用途也记在 `catalog.json`。
- `catalog.json` 新增三样：

  | 新增 | 内容 |
  |------|------|
  | 用途清单 | 有序的数组，顺序就是主菜单上的顺序。每项是一个标识（小写 kebab-case）和中英文名称 |
  | 第三方 Skill 的数组 | 每项除了条目共有的名字、中英文说明、官方链接之外，有：来源（GitHub 上的「所有者/仓库」）、其中的 skill 清单（至少一个；每个是 skill 自己声明的名字和中英文说明）、可选的宿主限制（写法同 MCP 的） |
  | 本仓库 skill 的用途（可选） | 按 skill 的名字给出一个用途。只有要另外出现在某个用途下的才写；不写的只在「推荐」里 |

- MCP、工具、外部项目、第三方 Skill 的条目各多两个字段：用途（用途清单里的一个标识）和可选的推荐标记（布尔）。
- 第三方 Skill 的名字只在它自己的数组里唯一，和别的数组的规矩一样。
- 初始的 10 个用途，按这个顺序：开发工作流与规范、Agent 行为约束与输出风格、代码库索引与理解、上下文记忆与 Token 优化、联网搜索与文档检索、浏览器自动化、UI 设计图像与视频、文档处理、提示词与写作、代码审查评估与安全。
- **「推荐」由两部分组成**：本仓库的全部 skill（自动，凡是维护者放进仓库的都算），加上带推荐标记的其它条目。本仓库的 skill 不靠标记进入「推荐」，也去不掉。

### 读取与校验

- 本仓库 skill 以外的条目有且只有一个用途。新版安装器读到没有用途、或用途不在清单里的这类条目，把它连同原因记进「被跳过的条目」，其余照常。这沿用现在「写坏的条目只跳过那一条」的做法。
- 本仓库的 skill 没有用途是正常的：它只出现在「推荐」里。给它写的用途不在清单里时，只是不在任何用途下出现，「推荐」里照常有它，并在目录校验命令里报出来。
- 第三方 Skill 的来源和其中每个 skill 的名字会拼进一条外部命令的参数，所以只收安全的字符：来源是两段由字母、数字、点、下划线、连字符组成的词，中间一个斜杠；skill 的名字是字母或数字开头，后面只有字母、数字、点、下划线、连字符。这和 MCP 启动命令的词只收安全字符是同一个理由。
- 目录校验命令照新规则查，并在通过时的那一行里报出第三方 Skill 的个数；每条新规则都有一句给人看的说法。
- 用途清单本身写坏（不是数组、标识重复、缺名称）时，受影响的条目按「用途不在清单里」处理，不让整份目录读不了。

### 主菜单与流程

- 主菜单的行依次是：推荐（里面有条目才有）、有条目的各个用途（按用途清单的顺序）、退出。每行有名称、条目数。按类型分的四个入口取消。
- 进入「推荐」或一个用途之后的顺序固定为：选宿主（检测到不止一个才问）→ 选安装范围 → 混合列表 → 含多个 skill 的第三方 Skill 各自的清单 → 逐个 MCP 问 key → 汇总与将执行的命令 → 确认 → 覆盖前的单独询问 → 执行 → 结果 → 外部项目的说明与链接 → 回主菜单。
- 安装范围每次进入列表都问，光标起始在全局。一次运行里再次进入时，起始位置仍是全局，不记上一次的选择。
- 混合列表里组件在上、外部项目在下，两段之间有分隔。组件按类型分段，顺序是 Skill（本仓库的）、第三方 Skill、MCP、工具；段内带推荐的在前，其余按名字。类型不占一栏，写在段首的标题里。
- 状态每次进入列表都现探测，这一点不变。本仓库的 skill 和 MCP 每个所选宿主各有一个状态；第三方 Skill 同样每个宿主一个；工具只有一个状态，与宿主和范围无关；外部项目没有状态。
- 三种类型原有的规矩原样带进混合流程，不因为合在一起而放松：命令先完整展示、确认了才执行、展示的和执行的是同一份；本仓库的 skill 遇到不是本工具装的目录逐个另问、缺省不覆盖；工具的成败只看复核；key 的值只进内存和命令参数；一项失败不影响其余项。
- 执行的先后：本仓库的 skill → 第三方 Skill → MCP → 工具。工具放最后，因为它的命令会直接接管终端的输入输出。
- 只勾了外部项目时没有要执行的东西，不出现汇总确认，直接列出说明与链接。

### 安装范围

- 「项目」是运行安装器时所在的目录。它作为运行环境的一个事实从入口传进来（和主目录、临时目录同样的方式），入口仍然不直接碰进程；测试里它是一个临时目录。
- 宿主适配多回答三个问题：项目范围的 skill 目录在哪、项目范围的 MCP 怎么添加和移除、去哪看项目里已经配了哪些 MCP。
- 两个宿主项目范围的 skill 目录，与那个通用安装程序不带全局选项时落的位置一致：Claude Code 在项目目录的 `.claude/skills`，Codex 在项目目录的 `.agents/skills`。
- 界面上不为项目路径单独设确认。汇总里各项的位置照常显示，项目范围的写成相对当前目录的路径。
- 工具没有安装范围：选了项目，工具仍照原样装，汇总里不给它写范围。

### 第三方 Skill 的安装

- 调用的是 Vercel 的 skills CLI，经 `npx` 起：给出来源、要装的 skill 的名字、目标宿主、跳过确认；装到全局时再加全局选项。**每个宿主单独调用一次**——一次只给一个宿主时落下的是真实目录，结果也天然各自独立，和「装进两个宿主就各走一遍」的既有决定一致。
- 用**不经 shell、不接终端**的那种执行方式（现在装 MCP 用的那一种）：命令和参数分开传，命令的输出不上屏，它也读不到用户的输入。这样它自己的字符画和框线到不了终端，也没有机会提问。
- 外部命令执行器的这种方式多收两样可选的东西：在哪个目录下运行（项目范围要在项目目录下运行），以及额外的环境变量（用来关掉 skills CLI 的遥测）。工具用的 shell 方式不变。
- **成败看复核，不看退出状态**，和工具一样：命令结束后，目标位置下那个 skill 的目录里有 `SKILL.md` 才算装上。
- **失败原因不转述那个程序的话**，沿用「失败原因里不转述宿主命令的话」的既有决定：结果行只说哪一步、退出状态几，或「没能运行」加错误码。完整的命令在汇总里，用户可以照着自己跑。
- 状态只有两种：目标位置下有这个 skill 的目录就是已安装，否则未安装。不比较版本，不写安装标记。条目含多个 skill 时，列表里那一行写「已装几个 / 共几个」，清单里各写各的。
- 目标位置已有同名目录时，确认之后、执行之前逐项另问，缺省不覆盖——skills CLI 自己遇到同名目录是直接覆盖的。
- skills CLI 的版本钉在实测过的主版本（1.x）上，写在安装器的代码里，不随它的最新版漂移。
- 条目写了宿主限制的，在不支持的宿主下显示不支持、不产生安装项，做法同 MCP。
- 汇总下方固定一行提醒：第三方 Skill 装的是作者当时的最新版，维护者没有逐版检查。

### MCP 的项目范围

- Claude Code：用它添加和移除命令自带的项目范围；已配置的 MCP 从项目目录的 `.mcp.json` 里看。
- Codex：它的添加命令没有范围选项，官方只说项目目录里可以放一份配置、只对受信任的项目生效。做法在实现的第一步验证；验证的结论和选定的写法先记进「安装 MCP」的规范再动手。验证不通过时，项目范围下 Codex 那一栏显示不支持并写明原因，不拿没验证过的写法去改用户的文件。
- 选了项目范围且这一轮有 MCP 要装进 Codex 时，汇总下方有一行说明：Codex 只对受信任的项目读这份配置。
- 选了项目范围且这一轮有带 key 的 MCP 时，汇总下方有一行警告，写明 key 会以明文写进哪个文件、不要提交。它在确认之前出现。
- 全局范围的行为一个字不变。

### 外部项目

### 上游核对命令

  - 工具：安装命令在维护者的虚拟机里跑通、复核通过。本任务里没有条件跑的一律先作为外部项目。
- 已在仓库里的 archify、onetake、unlazy、shuorenhua 保持为本仓库的 skill，不改成第三方 Skill。

## Testing Decisions

- **好的测试只断言对外的行为**：给定一份目录、主目录和项目目录的初始状态、环境和一串应答，看终端上输出了什么、退出状态是几、记录到了哪些命令、主目录和项目目录里有什么。不为内部模块单独写测试。
- **不新增接缝。** 主接缝仍是安装器入口，经测试架子；辅助接缝仍是把开发命令当子进程跑、只断言输出和退出状态（目录校验命令的先例）。上游核对命令走辅助接缝：让它对着一个本地的假仓库目录跑，联网的那一段不进自动化测试，手动核对。
- **测试架子要跟着长三样**：样例目录里有用途清单、第三方 Skill 和本仓库 skill 的标注；可以给一个项目目录；只记录不执行的命令执行器要能在「执行」某条命令时往目标位置放文件（模拟 skills CLI 装上了）或不放（模拟没装上），并记下那条命令是在哪个目录、带着哪些额外环境变量运行的。工具的测试里已有「命令执行后复核」的先例。
- **现有按类型分组的用例要搬家**：它们从主菜单进「Skill」「MCP」「工具」「应用项目」，入口没了。断言的行为（状态、覆盖、key、命令、复核、出错矩阵）一条都不能丢，改成从用途进入后再断言。
- **新增的用例至少覆盖**：
  - 主菜单：用途的顺序与条目数、空用途不出现、「推荐」有与无。
  - 混合列表：四种类型同表、外部项目在后、标记、没有宿主时组件不可选。
  - 一次勾选三种组件加一个外部项目：汇总里都有，命令的先后，结果各一行，最后是外部项目的链接，没有调用链接打开器。
  - 安装范围：本仓库的 skill 落在项目目录；第三方 Skill 的命令不带全局选项且在项目目录下运行；Claude Code 的 MCP 命令带项目范围；状态按范围读。
  - 第三方 Skill：单个 skill 的直接装；多个的出清单、勾几个装几个、一个不勾则不装；记录到的命令逐字正确（来源、名字、宿主、跳过确认、全局与否）、每个宿主一条；带着关遥测的环境变量；用的是不接终端的执行方式；命令退出 0 但目标位置没有 `SKILL.md` 时判失败；退出非 0 时结果行的写法；已有同名目录时另问且缺省不覆盖；宿主限制。
  - 项目范围带 key 的 MCP：警告出现在确认之前，警告里没有 key 的值。
  - 读取与校验：没有用途、用途不在清单里、第三方 Skill 的来源或名字不合规则——各自被跳过并带原因；旧格式的目录（没有新增的三样）读得了且不崩。
  - 推荐：本仓库的 skill 不带任何标注也在「推荐」里、且不在任何用途下；写了用途的同时出现在两处；带推荐标记的 MCP 同时出现在「推荐」和它的用途下。
  - 目录校验命令：上面每种写坏的情况各有一句说法，退出状态非零。
- **提问实际打到终端上的东西**（空行、按键提示、收成一行）用真实交互库加脚本按键的跑法核对，先例是现有的提问用例。
- 观感仍由界面预览页加视觉评审把关，预览页为上表的每个状态各加一格。
- 测试在 Node 22.13 上再跑一遍。
