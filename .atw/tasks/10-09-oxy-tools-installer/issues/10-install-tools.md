## 实现时定下的事（除注明的两条外，维护者尚未逐条确认）

- 工具条目的字段名：`name`、`description`（`zh`、`en`）、`url`（官方链接，暂不显示）、可选的 `hosts`、`install`、`check`。`install` 是 `{ default, macos?, linux?, windows? }`：`default` 必须有，三个系统名各可另给一条命令，或给 `null` 表示这个系统不支持，别的键忽略。`check` 是 `{ command }`（一个不带目录的命令名）或 `{ path }`（主目录下的相对路径），恰好取一种。
- **安装命令是一整行，交给系统的 shell 去解释**（POSIX 上 `sh`，Windows 上 `cmd.exe`），输入输出直接接在用户的终端上——**维护者 2026-10-09 确认**。官方安装命令多是 `curl … | sh` 这样的管道，拆成「命令 + 参数」写不出来。它只收看得见的 ASCII 字符、首尾不留空格（没有换行、制表符、控制码和不可见的字符），执行前整行展示并确认，展示的和执行的是同一个字符串。这和 MCP 那边「不经过 shell」是两套口径。
- 外部命令执行器多了第三个参数 `{ shell: true }`：整行交给 shell，`stdio: 'inherit'`。命令要问话（`sudo` 的密码）也答得了。
- 安装器不认识的系统（`freebsd` 等）用 `default`。
- 工具不问装进哪个宿主；`hosts` 只决定可不可选：条目要的宿主一个都没**检测到**时不可选。**一个宿主都没检测到时工具分组和别的组件一样进不去**（规格：这时只有应用项目可进入）。
- 不可选的原因写在状态栏的位置（照 `ui-direction.md`）：`不支持 macOS` / `不支持 Linux` / `不支持 Windows`；宿主的原因也放在那里，沿用 MCP 那一句「需要别的 AI Agent」。
- 已安装的工具照样可选，再装一次就是再执行一遍命令，不另问。
- 成功与否只看复核：命令非零退出但复核通过算「已可用」，退出状态照实写在后面；命令以 0 退出而可执行路径上找不到它算失败，并提醒「可能要重开终端才找得到」；命令没能起来时原因只取错误码，照样复核。失败的原因不转述命令自己的话，它的输出就在上面。
- **一次装不止一个工具时，合计之前用一个「结果」分区把各项的结论集中再列一遍**——**维护者 2026-10-09 定的**（评审后加的：设计稿只画了一个工具，结论紧跟输出；输出一长，前面的结论就滚出屏幕，和用户故事 40 的「在最后看到逐项的成功或失败及原因」对不上）。只装一个时不重复。
- `catalog.json` 三类条目都校验之后，`Catalog.unread` 和目录校验命令的「未校验」一行整个去掉；通过信息多数一类（`N 个 skill、M 个 MCP、K 个工具、J 个应用项目`）。
- 结果行和合计抽成了 `ui.ts` 的 `tally()`，skill、MCP 的「正在安装」分区和工具的执行分区共用（评审后改的：原先工具这边另抄了一遍）。
- 测试架子：`commandResult` 多了第三个参数 `{ home }`（这次运行的临时主目录），`result.commands` 里整行交给 shell 的多一个 `shell: true`。

## 评审后没有改的

- **复核看的是启动时的 `PATH`**。安装脚本改的是 shell 的启动文件，新装的目录这次运行里不在 `PATH` 上，`check.command` 会判失败（结论里有重开终端的提醒）。这种工具该用 `check.path` 登记；设计稿里 uv 装进 `~/.local/bin` 后显示「已可用」，按现在的实现只有那个目录本来就在 `PATH` 上才会这样。
- **`check.path` 不套 `PATHEXT`，`check` 也不能按系统覆盖**。Windows 上叫 `bun.exe`、别处叫 `bun` 的文件，用路径检查就得选一个各系统上都一样的路径。要不要让 `check` 也能按系统覆盖，**需要维护者定**。
- 命令的输出不以换行结尾时，结论上方的那个空行只是把那半行收掉，结论会贴着输出。输入输出直接接在终端上，呈现层看不到它最后一个字符。
- 执行中按 Ctrl+C，安装器随即以 130 退出，已经装完的那些没有合计。和下载 skill 时一样。
- 已装着的工具重装失败仍显示「已可用」（退出状态写在后面）：规格说以复核为准。
- 宿主的原因顶替了状态，那一条看不到已安装还是未安装；英文的 `needs another AI Agent` 把状态栏撑到 22 列。视觉评审建议让原因越过栏界占说明的位置。
- 工具名很长时命令被挤窄（名字栏按最长的名字定宽）。视觉评审建议有命令放不下时改成名字独占一行；没有改，那是改版式。
- 「已可用，…」用逗号接、「失败 …」用空格接；英文的 `failed the command exited…` 读着别扭。后者是工单 03 起结果行一直的写法。
- 代码上的判断题：`ToolResult.run` 与 `McpInstallProblem.cause` 是同一个形状，`errorCode` 仍住在 `install-mcp.ts`（注释讲的是 key）；`entryPicker` 的 `reasonAsStatus` 是逐行的布尔值而实为整张表的属性；`CommandOptions { shell: true }` 靠注释约定 `args` 是空的；系统名有三张表（`catalog.ts`、`install-tool.ts`、`messages.ts`）；`toolResult` 通过时返回以标点开头的半句；`toolCommandList` 与 `commandList` 骨架相同。

## 没有验证的

- 真实的命令执行器不进自动化测试。手动核对过两样：用小脚本直接调它（管道的输出上屏、`exit 3` 得到 3、不存在的命令得到 127、不经 shell 的那一支输出仍不上屏）；构建后用 `expect` 在伪终端里经安装器走了一遍（`HOME` 和 `OXY_TOOLS_CATALOG` 都 `export` 到临时目录，样例工具的命令里带一个 `read`）：输出上屏、键盘输入到得了命令、结论是「已可用」、之后主菜单还能操作。
- Windows 经 `cmd.exe` 的那一支没有在真机上跑过。
- 没有用真实的工具条目验证过（目录里还没有）；预览页和测试里的命令都是假的，从不真的执行。
- 测试在本机的 macOS 上用 Node 24 和 22.13.0 各跑过一遍；Linux 和 Windows 要等推送后由 CI 跑。
