## 实现时定下的事（除注明的一条外，维护者尚未逐条确认）

- 条目的字段名是 `name`、`description`（`zh`、`en`）、`url`（官方链接，暂不显示）、可选的 `hosts`、`server`。宿主在目录里的标识是 `claude-code`、`codex`；`hosts` 写了就不能为空，里面不认识的标识留着不管（以后加了宿主，旧版安装器照样读得了）。`server` 是 `{ "command": …, "args": […] }`（本地进程，`args` 可省略）或 `{ "url": … }`（远程地址，只指可流式的 HTTP），恰好取一种。
- `server.command` 和 `server.args` 的每一项只收字母、数字和 `@ : / . _ = + , ~ -`；`server.url` 与应用项目的 `url` 同一条规则。它们会原样显示给用户确认、交给宿主的命令、之后每次启动都被执行，所以不许有空白、引号和 shell 会另作解释的字符。代价是带空格或引号的参数、带查询串的网址参数、Windows 路径写不进目录。要放宽，改 `catalog.ts` 的 `COMMAND_WORD`。
- 两个宿主的命令写法对照了官方文档，并在本机用 claude 2.1.295、codex 0.162.0 在临时配置目录里实测（添加、重复添加、移除不存在的各是什么结果、配置写到哪）：`claude mcp add --scope user <名字> -- <命令…>`、`claude mcp add --scope user --transport http <名字> <网址>`、`claude mcp remove --scope user <名字>`；`codex mcp add <名字> -- <命令…>`、`codex mcp add <名字> --url <网址>`、`codex mcp remove <名字>`。
- **原生 Windows 上不给本地进程包 `cmd /c`**，各系统上命令相同。Claude Code 的旧文档要求过；它的更新日志 2.1.119 写明移除了那条“需要 cmd /c 包装”的警告（称其为误报），现行的 MCP 文档里已经没有这条说明；Codex 的文档从未要求过。2.1.119 之前的 Claude Code 因此不在支持之列。
- 看 MCP 配没配过：Claude Code 是 `<配置目录>/.claude.json` 顶层的 `mcpServers`，Codex 是 `<CODEX_HOME>/config.toml` 的 `mcp_servers` 表；认 `CLAUDE_CONFIG_DIR` 和 `CODEX_HOME`（宿主的命令会写到那里）。文件不存在算未配置；读不了、解析不了、那里不是对象才是未知。
- **状态未知时先尝试移除同名配置再添加**，移除失败不算失败。汇总里这一行的操作写「添加」（说不出是新装还是覆盖），备注「状态未知，先尝试移除同名配置」，两条命令都照实列出。理由：Claude Code 遇到同名会失败、Codex 会直接覆盖，先移除让两边的结局一样，也和状态已知时再装一次的结局一样。
- 已配置的再装一次不另问，先移除再添加；移除失败就不添加；移除成功而添加失败时，结果里写明「此前已执行移除」（旧配置这时已经没了）。
- 失败的原因只写哪一步和退出状态（或命令起不来时的错误码）。宿主命令的输出不上屏，也不转述。
- 所选宿主一个都不支持的条目：勾选位是 `–`，行尾写「需要别的 AI Agent」。多选没有办法指定光标的起始位置，光标可能一开始就停在这种行上。
- 装 MCP 时的「装进哪些 AI Agent」只写名字，不写目录。
- 目录校验命令的通过信息多数一类：`目录校验通过：11 个 skill、0 个 MCP、0 个应用项目`。
- 新增两个运行时依赖：`smol-toml`（读 Codex 的 `config.toml`，零依赖）和 `cross-spawn`（Windows 上经 `cmd.exe` 起 `.cmd` 并转义参数，连依赖共 6 个小包），外加开发依赖 `@types/cross-spawn`。
- **维护者已定的一条**（2026-10-09）：Codex 添加远程地址的 MCP 时，服务器支持 OAuth 的话会当场打开浏览器登录并等它完成，授权网址打在它自己的输出上，而安装器不显示宿主命令的输出。在“汇总里提醒”“把宿主的输出透传到屏幕上”“另开工单”三个方案里选了第一个：有远程地址的 MCP 要装进 Codex 时，将执行的命令下面多一行「注意」，并给出事后补登录的命令 `codex mcp login <名称>`。

## 评审后没有改的

- `CommandRunner` 仍是 `(command, args)` 两个参数，而已经有了 `Command` 这个类型。
- `McpStatus` 里混着 `unsupported`（它说的是条目与宿主的关系，不是配置的状态），于是 `Exclude<McpStatus, 'unsupported'>` 出现了三处；`mcpStatuses` 返回的二维数组靠下标与 `mcps`、`hosts` 对应。
- `ui.mcpSummary` 与 `ui.installSummary` 形状相近，各写了一份；展示命令时判断要不要加引号的 `PLAIN_ARGUMENT` 与目录校验用的 `COMMAND_WORD` 是两个相近的字符集。
- `runMcpJobs` 不看 `interrupt`：真实运行时 Ctrl+C 由 `bin.ts` 直接退出，宿主的命令和安装器在同一个前台进程组里会一并收到信号；只是测试接缝里没有“执行中途按 Ctrl+C”这一条。
- 同一份宿主适配里，看 MCP 的配置认 `CLAUDE_CONFIG_DIR`，skill 目录不认（仍是 `<主目录>/.claude/skills`）。改 skill 目录不在本工单的范围内。
- 视觉评审提过不可选的原因写成「仅支持 Codex」更有用；没有改，因为一个都不支持时，条目支持的可能是这一版还不认识的宿主。浏览器打不开时这一项会一直显示进行中，直到用户按 Ctrl+C——这是所选方案已知的代价。

## 没有验证的

- 真实的外部命令执行器不进自动化测试（测试里的执行器只记录）。本机用一个假的宿主命令核对过：参数原样逐个传到（含带 `&`、`'`、`$` 的网址）、非零退出、命令不存在、它的输出没有漏到终端上；并在临时的 `CLAUDE_CONFIG_DIR` 和 `CODEX_HOME` 下用真实的 `claude` 和 `codex` 经安装器端到端走过新装和覆盖两遍（真实的配置没有动）。**Windows 上经 `cmd.exe` 起 `.cmd` 的那一支没有在真机上跑过。**
- “原生 Windows 上不需要 `cmd /c`”来自文档和更新日志，没有在 Windows 真机上实测。
- 测试在本机的 macOS 上用 Node 24 和 22.13.0 各跑过一遍；Linux 和 Windows 要等推送后由 CI 跑。
- 没有用支持 OAuth 的真实远程 MCP 走过 Codex 当场登录的那条路（会弹出维护者的浏览器）；这个行为是读 Codex 的源码 `codex-rs/cli/src/mcp_cmd.rs` 确认的。
