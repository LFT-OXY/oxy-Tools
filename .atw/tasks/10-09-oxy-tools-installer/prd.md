> 术语以仓库根 `GLOSSARY.md` 为准。位置与分发方式的取舍见 ADR-0001、ADR-0002。

## Problem Statement

维护者在 oxy-Tools 仓库里策展了一批 skill，今后还会加入 MCP、工具和应用项目。现在想用这些东西的人没有一个统一入口：

- 装 skill 只能手动复制目录，或者借道 A Team Workflow 的 `atw init`——而后者只装进当前项目，且只管 skill。
- 装 MCP 要自己查每个宿主的配置写法；需要 API key 的，还要自己找去哪申请、填到哪。
- 装工具要逐个翻官方文档找安装命令。
- 那些没法一键安装的项目（比如要用 docker 部署的框架），没有地方集中展示。

对维护者来说，目录一旦和安装程序绑在一起，每增删一个条目就得发一次 npm 版本。

## Solution

一个发布到 npm 的交互式安装器。用户运行 `npx oxy-tools`，看到维护者策展的目录，按类型挑选：

- **skill、MCP、工具**这三种组件，选中后由安装器装进用户机器上的 Claude Code 或 Codex（用户级，对所有项目生效）。需要 API key 的 MCP，安装器给出申请链接，用户粘贴 key 后写入宿主配置。
- **应用项目**只展示说明并打开官方链接，由用户自己按文档安装。

目录数据放在 oxy-Tools 仓库里，安装器每次运行时现拉，所以维护者增删条目只需要提交仓库。

界面要美观：视觉方向由维护者在动手前从设计稿里选定，在深色和浅色终端下都要好看。

## User Stories

**浏览目录**

1. 作为用户，我想用一条 `npx oxy-tools` 命令启动安装器，这样不用先安装或配置任何东西。
2. 作为用户，我想看到目录按 skill、MCP、工具、应用项目分组，这样能直接进入我关心的那一类。
3. 作为用户，我想在列表里看到每个条目的一句话说明，这样不用点开链接就能判断要不要。
4. 作为中文用户，我想看到中文界面和中文说明，这样读起来不费力。
5. 作为非中文用户，我想看到英文界面和英文说明，并能用一个启动参数强制指定语言。
6. 作为用户，我不想看到没有任何条目的分组，这样菜单里不会出现点进去是空的选项。
7. 作为用户，我想在目录加载时看到正在加载的提示，这样知道程序没有卡住。

**宿主**

8. 作为同时装了 Claude Code 和 Codex 的用户，我想选择把组件装进哪一个或两个都装，这样两边的工具链可以保持一致。
9. 作为只装了其中一个宿主的用户，我不想被问"装进哪个宿主"，这样少一步无意义的选择。
10. 作为没装某个宿主的用户，我想被明确告知它没被检测到并被跳过，这样不会以为装成功了。
11. 作为两个宿主都没装的用户，我仍想浏览应用项目并打开链接，同时被告知组件暂时装不了以及原因。
12. 作为用户，我不想看到只支持另一个宿主的组件出现在我选的宿主下，这样不会选到装不上的东西。

**安装 skill**

13. 作为用户，我想一次勾选多个 skill 一起安装，这样不用重复操作。
14. 作为用户，我想让 skill 装到用户级目录，这样它在我所有的项目里都可用。
15. 作为用户，我想在列表里看到哪些 skill 已经装了以及装的是哪个版本，这样知道自己的现状。
16. 作为用户，我想在已装版本和目录版本不同时同时看到两个版本号，这样能自己决定要不要重装。
17. 作为用户，我想对已装的 skill 再装一次就能覆盖成最新版，这样更新不需要另一套操作。
18. 作为已经手动放过同名 skill 的用户，我想被告知"该目录已存在且不是本工具装的"，并在覆盖前被单独询问，这样我自己的东西不会被悄悄替换。
19. 作为用符号链接管理 skill 的用户，我想让安装器把链接当作"不是本工具装的"来对待，且覆盖时只替换链接本身，这样链接指向的原目录不会被改动。
20. 作为用户，我想在安装一个体积很大的 skill 前看到它的说明里的体积提示，并且安装时只下载这一个 skill，而不是整个仓库。
21. 作为用户，我想在下载中途失败或被我中断时不留下装了一半的 skill，这样宿主不会加载到残缺内容。

**安装 MCP**

22. 作为用户，我想勾选 MCP 后由安装器替我写好宿主配置，这样不用学每个宿主的配置写法。
23. 作为用户，我想在安装需要 API key 的 MCP 时看到去哪申请的链接，这样知道下一步该做什么。
24. 作为用户，我想粘贴 key 时输入内容不回显，这样旁人看不到。
25. 作为用户，我想跳过标为可选的 key，这样没有它也能先装上。
26. 作为用户，我想在漏填必填 key 时只跳过这一个 MCP，其余选中的照常安装。
27. 作为把同一个 MCP 装进两个宿主的用户，我想只输入一次 key，这样不用重复粘贴。
28. 作为用户，我想确信安装器不保存也不打印我的 key，它只出现在宿主自己的配置里。
29. 作为用户，我想在列表里看到哪些 MCP 已经配置过，并且再装一次就能覆盖旧配置。

**安装工具**

30. 作为用户，我想勾选工具后由安装器执行它的官方安装命令，这样不用自己去翻文档。
31. 作为用户，我想在任何命令执行前看到将要执行的完整命令并确认，这样不会有我不知道的东西在我机器上运行。
32. 作为用户，我想实时看到安装命令的输出，这样出错时能看到原因。
33. 作为用户，我想在命令跑完后被告知工具是否真的可用了，这样不会把"命令退出了"误当成"装好了"。
34. 作为 Windows 用户，我想拿到适用于 Windows 的安装命令；如果某个工具不支持我的系统，我想看到它被标出来而不是装到一半失败。

**应用项目**

35. 作为用户，我想浏览应用项目的列表和说明，这样了解维护者推荐了哪些需要自行部署的项目。
36. 作为用户，我想选中一个应用项目后在默认浏览器里打开它的官方链接。
37. 作为在远程终端里使用的用户，我想同时看到链接的文本，这样浏览器打不开时可以自己复制。

**确认、结果与出错**

38. 作为用户，我想在动手前看到一份汇总：要装什么、装进哪里、哪些会被覆盖，确认后才执行。
39. 作为用户，我想在确认之前能返回上一步改选，这样选错了不用重来。
40. 作为用户，我想在一次安装多项时，某一项失败不影响其余项，并在最后看到逐项的成功或失败及原因。
41. 作为用户，我想在安装完成后回到主菜单，这样能接着装别的类型。
42. 作为用户，我想随时按 Ctrl+C 干净退出。
43. 作为没联网的用户，我想看到"无法读取目录"的明确提示，而不是一段堆栈。
44. 作为使用旧版安装器的用户，我想在目录格式已经升级时被提示如何升级安装器，而不是看到错乱的列表。
45. 作为短时间内反复安装 skill 而触发 GitHub 限流的用户，我想看到原因和两个出路：稍后再试，或设置访问令牌。
46. 作为在脚本或管道里误运行它的用户，我想被告知它需要交互式终端并以非零状态退出。

**维护者**

47. 作为维护者，我想往仓库提交一个 skill 及其清单条目后，用户下次运行就能看到它，不用发 npm 版本。
48. 作为维护者，我想在一个文件里登记 MCP、工具和应用项目，格式不同于 skill 清单，互不干扰。
49. 作为维护者，我想为每个条目声明它支持哪些宿主，省略时表示全部支持。
50. 作为维护者，我想为 MCP 声明它需要哪些 key、是否必填、去哪申请，这样安装器能替我向用户解释。
51. 作为维护者，我想为工具声明分操作系统的安装命令和"怎么算装好了"的检查方式。
52. 作为维护者，我想在提交前用一条命令校验目录数据，并在推送后由 CI 再校验一次，这样不会推上一份安装器读不了的目录。
53. 作为维护者，我想在本机把安装器指向本地的目录数据，这样推送前就能看到新条目在界面里的样子。
54. 作为维护者，我想在目录里出现一条写坏的条目时只有这一条被跳过，其余条目照常可用。
55. 作为维护者，我想让 `cli/` 完全自成一体，这样将来要搬到独立仓库时可以原样搬走。

**A Team Workflow**

56. 作为 A Team Workflow 的用户，我想让 `atw init` 的额外 skill 安装在这次改动之后照常工作。
57. 作为 A Team Workflow 的维护者，我想让安装 skill 的那部分逻辑以目标目录为参数，这样下一步可以让 `atw init` 直接调用本安装器。

**界面观感**

58. 作为用户，我想看到一个排版清晰、配色讲究的界面，这样用起来舒服，也愿意把它推荐给别人。
59. 作为用浅色终端的用户，我想让界面在浅色背景下和在深色背景下一样清晰好看。
60. 作为关闭了终端颜色的用户，我想让界面在没有颜色时仍然能读懂每个状态。
61. 作为维护者，我想在写代码之前就在浏览器里看到每个画面的样子，并从几种风格里选一种，这样风格由我决定而不是做完才知道。
62. 作为维护者，我想用一条命令把安装器真实的终端输出生成一个网页，这样每次改动后都能看到实际效果有没有走样。
63. 作为用户，我想在启动安装器时最先看到一个醒目的 OXY 大标志，这样一眼知道自己进的是这个安装器。

## Implementation Decisions

**位置与工程形态**

- 安装器是一个 TypeScript 写的 Node 命令行程序，源码在仓库的 `cli/` 目录，从该目录发布为 npm 包 `oxy-tools`，可执行命令同名。要求 Node 22.13 及以上的 22.x，或 23.5 及以上（原定 22 及以上，去掉所选交互库不支持的版本）。
- `cli/` 自带包描述文件，仓库根目录不放；安装器运行时只通过目录来源读数据，不引用 `cli/` 以外的任何文件；构建和测试只扫描 `cli/` 内部（`skills/` 下的上游整包自带测试和包描述文件，不能被扫进来）。
- npm 包只含构建产物，不含任何 skill 内容，也不含目录数据。
- 交互界面使用一个成熟的现成命令行交互库（需支持多选、隐藏输入、Windows 终端），不自写列表控件，不接管终端输入。选定为 `@inquirer/prompts`；选它的理由和实测得到的用法见 `ui-direction.md`。

**模块划分**

安装器对外只有一个入口，内部分五块，全部经入口被测到：

- **目录**：读取并校验 skill 清单与 `catalog.json`，合并成统一的条目集合。
- **宿主适配**：每个宿主一份，回答四个问题——宿主在不在、skill 装到哪个目录、怎么拼出添加和移除 MCP 的命令、去哪看某个 MCP 是否已配置。
- **安装**：三种组件各一个安装动作。安装 skill 的动作只接受"条目 + 目标目录"，不知道宿主的存在。
- **状态探测**：给出每个组件在每个宿主下的状态。
- **交互流程**：菜单、选择、汇总确认、结果展示。

入口接受五样可替换的外部依赖：目录来源、用户主目录、外部命令执行器、提问器、链接打开器。正式运行时用真实实现，测试时全部替换。放临时文件的目录和“提问之外按了 Ctrl+C”的信号也由调用方传入，它们和启动参数、环境变量一样是运行环境的事实，不算外部依赖。

**界面呈现**

- 所有终端输出都经过同一个呈现层，由它统一决定配色、符号、间距、边框和标题区；其余模块只说"显示什么"，不自己拼样式。
- 颜色用终端的标准命名色表达，实际色值由用户自己的终端配色决定；因此每种状态都必须在不显示颜色时仍能靠文字或符号区分。
- 环境变量 `NO_COLOR` 存在（哪怕为空）或输出不是终端时不输出颜色，粗体和暗淡也一并不输出；不理会 `FORCE_COLOR`，两者同时设置时以 `NO_COLOR` 为准。
- 界面预览页：一条仅供开发使用的命令，经主接缝按预设场景驱动安装器，把真实的终端输出（含样式）渲染成一个离线 HTML 页面，每个画面一格，各有深色和浅色两种终端背景。它是生成物，不提交，不随 npm 包发布。每张涉及界面的工单把自己的画面作为场景加进去。

**目录数据的契约**

- 目录由仓库根目录的两个文件组成：`index.json`（skill 清单，格式保持现状，不改）和新增的 `catalog.json`。
- `catalog.json` 的顶层是一个整数格式版本号（从 1 开始）和三个数组：MCP、工具、应用项目，键名依次是 `version`、`mcps`、`tools`、`apps`。初始提交时三个数组都为空。
- 三类条目共有的字段：名字（组内唯一，字符集与 skill 名相同）、中英文一句话说明、官方链接。MCP 和工具另有一个可选的"支持的宿主"列表，省略表示全部支持。
- MCP 条目另有：
  - 连接方式，二选一：本地进程（启动命令和参数），或远程地址（一个网址）。
  - 环境变量列表，每项含变量名、是否必填、中英文说明、申请链接。环境变量只适用于本地进程方式。
- 工具条目另有：
  - 安装命令：一条默认命令，可按操作系统覆盖；某个系统被显式标为不支持时，安装器在该系统上把它显示为不可用。
  - 检查方式，二选一：某个命令在不在可执行路径上，或用户主目录下某个相对路径存不存在。
- 应用项目条目只有共有字段。
- 兼容规则：新增可选字段不升版本号，安装器忽略不认识的字段；不兼容的改动必须升版本号。安装器遇到高于自己所支持的版本号时，提示升级命令并以非零状态退出，不尝试解析。
- 单条条目校验不通过时跳过该条并在界面上提示被跳过的数量，不影响其余条目。会成为文件系统路径的字段（名字、skill 的路径）必须拒绝绝对路径、`..` 和空段。

**目录来源**

- 默认从 GitHub 上本仓库 `main` 分支的原始文件地址读取两个目录文件，只走 HTTPS。
- 可通过一个环境变量把目录来源改为本地目录，供维护者预览和测试使用。此时 skill 内容也从该本地目录读取。

**skill 的下载与安装**

- 按 skill 单独下载，不下载整个仓库（整包约 211MB）。先向 GitHub 查询当前提交及该 skill 目录下的文件列表，再逐个下载文件，全部钉在同一个提交上。一次运行里安装多个 skill 共用同一次查询。
- 未登录的查询受 GitHub 每小时限额约束；被限流时给出明确提示。若环境里有 `GITHUB_TOKEN`，查询时带上它（只带给查询，下载文件不带）。查询失败不让安装器退出：说明原因后回到主菜单。GitHub 给出的文件列表不完整时不安装。
- 文件先下载到临时目录，确认其中有 `SKILL.md` 后再整体替换到目标位置；失败或中断时清理临时目录，目标位置保持原样。
- 安装即整目录替换，目录内的本地改动会丢失；汇总确认时要说明这一点。
- 安装完成后在该 skill 目录内写入一个安装标记（`.oxy-tools.json`），记录名字、版本、来源提交和安装时间；目录来源是本地目录时没有来源提交。安装器没有任何集中的状态文件。

**宿主**

- 第一版两个宿主，列表可追加：
  - Claude Code：以 `claude` 命令是否可用判断在不在（看它在不在可执行路径上，不执行它）；skill 目录是用户主目录下的 `.claude/skills`；添加 MCP 用它自己的命令并指定用户级范围。
  - Codex：以 `codex` 命令是否可用判断在不在；skill 目录是用户主目录下的 `.agents/skills`（`.codex/skills` 已被 Codex 标为废弃）；添加 MCP 用它自己的命令。
- 写入 MCP 一律调用宿主自己的命令，不直接修改宿主的配置文件。宿主里已有同名 MCP 时，先用宿主的移除命令删掉再添加。
- 判断 MCP 是否已配置时，只读地查看宿主的用户级配置文件里有没有同名条目；读不了或格式不认识时，状态显示为未知，不报错。

**组件状态**

- skill 在某个宿主下有四种状态：未安装；已安装（本工具装的，显示已装版本）；已安装且与清单版本不同（同时显示两个版本）；已存在但不是本工具装的（目录存在而没有安装标记，或是一个符号链接）。
- 最后一种状态下，选中它需要在汇总之外单独确认覆盖，默认不覆盖。目标是符号链接时只替换链接本身。
- MCP 有三种状态：未配置、已配置、未知。
- 工具有两种状态：未安装、已安装，由条目声明的检查方式决定。

**API key**

- 安装含环境变量的 MCP 时逐个提问，显示说明和申请链接，输入不回显。必填项留空则跳过该 MCP；可选项留空则不传。
- 同一次运行里同一个变量只问一次，用于所有选中的宿主。
- key 只作为参数传给宿主的添加命令，安装器不写入任何文件、不打印、不出现在汇总和错误信息里。

**执行外部命令**

- 目录是运行时拉取的远程数据，而工具和 MCP 条目会导致命令被执行，因此任何外部命令在执行前都必须把完整命令展示给用户并取得确认（key 的值以占位符显示）。
- 工具的安装命令执行时输出直接透传给用户；结束后用条目声明的检查方式复核，以复核结果而不是命令的退出状态作为成功与否的依据。

**流程与退出**

- 启动后读取目录并探测宿主，然后进入主菜单；安装完成后回到主菜单。
- 语言默认按系统语言环境判断（中文环境用中文，其余用英文），可用启动参数强制指定。
- 没有交互式终端时不进入菜单，提示原因并以非零状态退出。另提供查看帮助和版本号的参数。
- 目录读取失败、目录格式版本不受支持时以非零状态退出；单个条目安装失败不改变退出状态，只在结果里列出。
- 出错说明写到标准错误，其余输出写到标准输出；这样标准输出被重定向到管道或文件时，用户在终端上仍然看得到出了什么错。

**仓库里随之要改的东西**

- 新增 `catalog.json`（三个空数组）。
- `.atw/spec` 增加 CLI 一层的规范；skills 层的概述改为"本仓库是目录加安装器"；清单与版本文档补上 `catalog.json` 的契约，以及对 A Team Workflow 的三条承诺（`main` 分支根目录的 `index.json` 及每条的四个字段、`path` 下有 `SKILL.md`、仓库可整包下载且不提交依赖目录和构建产物）。
- 仓库根新增一份简短的 README，说明仓库的两个用途和许可证的分目录归属；`cli/` 自带 MIT 许可证文件。
- 新增 CI：在 macOS、Linux、Windows 上跑安装器的测试；目录文件有改动时跑目录校验。

## UI and Design

这是终端界面，没有视口；视觉规范来自维护者选定的视觉方向。

**视觉方向**

已由维护者选定，完整结论在任务目录的 `ui-direction.md`，后续所有界面工单以它为准。摘要：

- 方向是「账本」：通栏横线分区、标题嵌在线里；条目排成表格，一条一行，每个宿主各占一栏状态；本机信息、提醒、出错的原因与下一步都写成“键 值”对齐的行。没有边框。
- 启动时最先打出 OXY 大标志（实心方块字，终端的默认前景色），产品名、版本号和一句话说明压在它右下角，下面一条通栏横线。
- 状态一律用词表达（如 `已装 2.16`、`2.0.0 → 2.1.0`、`非本工具安装`、`未装`），不显示颜色时文字一字不变。
- 黑白为主：青色只落在提问标记、光标、已勾选的框和进行中的转动符号上；绿是已就绪，黄是需要留意，红是失败与出错，暗淡是次要信息。名字、说明、路径、命令一律用终端的默认前景色。
- 列表里的说明过长会截断，光标所在行的说明全文显示在列表下方。
- 加载目录和安装进行中时，行首有一个转动的符号；除此之外没有动画。
- 按 80 列设计；折行、截断、对齐都由呈现层按显示宽度自己算。
- 交互库是 `@inquirer/prompts`。
- 美观的边界：只在配色、符号、间距、边框、标题区这些静态元素上发挥，且限于所选交互库在真实终端里做得出来的效果；唯一的例外是加载与进行中的转动符号，由呈现层自己输出。不为好看而自写交互控件，不做全屏界面。
- 深色和浅色终端都要好看；不显示颜色时仍可用。
- 实际效果用界面预览页核对：它渲染的是安装器真实的输出，是视觉评审对照 `ui-direction.md` 时用的画面证据。
- 选定时用的设计稿和对比页留在本机任务目录的 `prototype/`，不提交，选定后不再维护。

**画面**

- 启动：OXY 大标志，一次运行只出现一次。
- 加载：读取目录时的进行中提示。
- 主菜单：只列出有条目的分组，外加退出。
- 选择宿主：仅在检测到两个宿主、且要装的是 skill 或 MCP 时出现；默认全选。
- 选择条目：多选列表，每行是名字、状态标记和一句话说明；不支持所选宿主或当前系统的条目显示为不可选并注明原因。所选宿主里只有一部分支持的条目仍可选，只装进支持的那些，并标出哪个宿主不支持；所选宿主一个都不支持时才不可选。
- 填写 key：逐项提问，带说明和申请链接。
- 汇总确认：列出每一项将装到哪里、哪些会覆盖、将执行的完整命令；可确认、返回或取消。
- 执行与结果：逐项显示进行中、成功或失败，最后给出总览。
- 应用项目：单选列表，选中后显示说明和链接并打开浏览器。

**必须能在终端输出里核对的状态**

- 启动后最先出现 OXY 大标志；没有交互式终端时不出现。
- 目录为空的分组不出现在主菜单里。
- 一个宿主都没检测到时，主菜单上方有一行说明，且只有应用项目可进入。
- 四种 skill 状态各有不同的文字标记，不只靠颜色区分。
- 汇总画面里出现的 key 一律是占位符。
- 目录读取失败、格式版本不受支持、被 GitHub 限流、没有交互式终端，这四种情况各有一段说明原因和下一步的文字，且不出现堆栈。
- 界面预览页里每个画面在深色和浅色背景下都与 `ui-direction.md` 的选定方向一致：颜色与符号的用法、间距、边框、标题区。
- 中文界面下各列对齐不因中文字符宽度而错位。

## Testing Decisions

**什么是好的测试**：只经由对外行为断言——给定一份目录、一个主目录的初始状态和一串用户应答，断言结束后主目录里有什么、哪些外部命令被请求执行、终端上输出了什么。不断言内部模块之间怎么调用，不为内部模块单独写测试。

**两个接缝**

- **主接缝：安装器入口**。目录来源换成本地样例，主目录换成临时目录，外部命令执行器只记录不执行（并可预设结果），提问器按预设应答，链接打开器只记录。要覆盖的行为：
  - 把一个 skill 装进一个宿主、装进两个宿主；装完后有内容和安装标记。
  - 四种 skill 状态的显示；覆盖已装的；对"不是本工具装的"目录拒绝和同意覆盖两种走向；符号链接只替换链接本身。
  - 下载中途失败后目标位置保持原样。
  - 安装本地进程和远程地址两种 MCP，记录到的命令符合各宿主的写法；同名已存在时先移除再添加。
  - 带 key 的 MCP：必填留空被跳过、可选留空不传、两个宿主只问一次；所有终端输出里不出现 key 的值。
  - 工具：执行前展示命令并确认；按操作系统选命令；系统不支持时不可选；命令成功但检查不通过算失败。
  - 应用项目：记录到被打开的链接，且链接文本出现在输出里。
  - 宿主缺一个、两个都缺时的行为。
  - 空分组不出现；写坏的条目被跳过并提示数量；格式版本过高时提示升级并非零退出；目录读不到时的提示；被限流时的提示；没有交互式终端时的提示。
  - 一项失败不影响其余项，结果逐项列出。
- **辅助接缝：目录校验命令**。用安装器自己的校验逻辑检查仓库里真实的 `index.json` 和 `catalog.json`，CI 和维护者共用同一条命令。

**先例**：仓库里没有非上游的 TypeScript 测试。可参照的做法有两处——清单与版本规范里那段对 `index.json` 的校验脚本（检查什么、怎么报错），以及 `oxy-learning-hub` 校验脚本的自检模式（一条命令、明确的通过输出和退出状态）。

**界面观感不靠自动化测试把关**：测试断言文字内容，不断言颜色和版式。观感由界面预览页加视觉评审把关——每张涉及界面的工单生成预览页并对照 `ui-direction.md`，发布前再整体对照一遍。

**运行环境**：测试用 vitest，在 CI 的三个操作系统上都要通过。真实的宿主命令和真实的 GitHub 不进自动化测试；发布前由维护者在本机对两个宿主各手动走一遍 skill 和 MCP 的安装。

## Out of Scope

- 代装宿主（Claude Code、Codex 本身）。
- 卸载组件、环境体检、主动的更新提醒。
- 装进当前项目（项目级安装）。
- 直接从第三方仓库抓 skill；第三方 skill 须先整包收进本仓库。
- 让 A Team Workflow 的额外 skill 步骤调用本安装器，以及为此需要的项目级安装和非交互用法。本次只保证安装 skill 的动作以目标目录为参数。
- 修改 A Team Workflow 的任何代码。
- 往 `catalog.json` 里填具体条目——条目由维护者自己给出。
- 远程地址方式的 MCP 的请求头鉴权；这类 MCP 的登录交给宿主自己的流程。
- 记住语言偏好等任何跨次运行的设置。
- 自动发布流程；第一版由维护者手动发布。
- 为了好看而自写交互控件、全屏界面；除加载与进行中的那一个转动符号之外的任何动画。
- 把界面预览页或设计稿提交进仓库或放进 README。
- 处理仓库整包 211MB 的问题（见下）。

## Further Notes

- **仓库整包 211MB**：`onetake` 在仓库里被跟踪了三份（源，加上 `.claude/skills` 和 `.agents/skills` 下的两份安装副本）。本安装器按 skill 单独下载，不受影响；但 A Team Workflow 安装额外 skill 时下载的是整包。建议另行处理，不在本任务内。
- **`catalog.json` 起步为空**：条目格式是按两个宿主实际接受的配置方式定的，没有经过真实条目检验。维护者加入第一批真实条目时如果发现装不进现有格式，在第一版发布前可以直接改格式而不用升版本号。
- **应用项目是否分标签**：等有真实条目后再决定。
- **Windows 上的本地进程 MCP**：Claude Code 在原生 Windows 上对某些启动命令可能要求额外的包装写法，实现宿主适配时要对照官方文档核实，并由 CI 的 Windows 环境覆盖命令拼装的测试。
- **npm 包名**：`oxy-tools` 在访谈当天未被占用，实现开始时再确认一次。
- **提交方式**：本仓库直接提交到 `main`，不另开分支。
